# 一句需求，是怎样被 Codex 变成代码的？

很多人以为 AI 编程就是：你说一句话，它马上吐出一段代码。

但在真实项目里，“会写代码”只是整个过程里很小的一环。

一条看似简单的需求，例如“给登录功能增加单元测试”，背后至少要经过八步：

1. **接收需求**：先判断用户真正想改什么，哪些内容没有说清楚。
2. **读取仓库**：识别目录结构、技术栈、项目规范和已有实现。
3. **搜索上下文**：找到相关页面、函数、测试、依赖和调用关系。
4. **制定计划**：决定改哪些文件、按什么顺序修改、怎样避免影响其他功能。
5. **修改代码**：生成补丁，而不是重新写掉整个项目。
6. **运行测试**：通过终端执行测试、类型检查或构建命令。
7. **读取报错**：定位失败发生在实现、测试、环境还是原有代码。
8. **交付变更**：整理修改内容、验证结果和仍然存在的风险。

真正困难的地方，不是生成某一行代码，而是管理上下文。

一个真实仓库可能有几百甚至几千个文件。AI 不可能每次把所有内容都读一遍，它需要先搜索，再选择与任务最相关的文件放进上下文窗口。找错文件、漏掉规范，后面的代码即使语法正确，也可能改错位置。

第二个关键是工具与权限。

读取文件、执行命令、访问网络和操作 Git，并不是同一种权限。一个可靠的编程智能体需要知道自己可以做什么、哪些操作可能改变环境、什么时候需要用户确认。

第三个关键是测试反馈。

没有测试，AI 只能判断“这段代码看起来合理”；运行测试以后，它才能知道代码是否真的能工作。报错也不是终点，而是下一轮搜索、修改和验证的输入。

所以 Codex 更像一套软件工程闭环：

**理解 → 搜索 → 计划 → 修改 → 测试 → 纠错 → 交付**

真正的能力，不是会写代码，而是能在真实项目里闭环完成任务。

你更想看下一篇拆解“Codex Skill”，还是“AI 为什么会改坏代码”？
