# Browser publication protocol

Use this protocol only after the first exact confirmation has passed the publication gate.

1. Do not open the LOFTER editor until `publication_gate.approve_form_fill(run_dir, "确认发布")` succeeds, `build_upload_manifest` returns the approved manifest, and that exact object is atomically saved as run-local `upload-manifest.json`.
2. **REQUIRED SUB-SKILL:** Read `browser:control-in-app-browser` completely before any browser action. Follow that Skill for all page inspection, navigation, typing, uploads, and evidence capture. Publishing uses only the Codex in-app browser selected with `agent.browsers.get("iab")`. Do not automatically switch to Chrome, Edge, another external browser, or another browser session when login is missing.
3. Load `sources/draft-intent.json` and select the native LOFTER publisher before opening the editor. For `content_format: image_post`, open or reuse only `https://www.lofter.com/#publish=photo`; for `content_format: article`, use only `https://www.lofter.com/#publish=text`. Never create an image post inside the text editor, even if the cover would be its first effective content node. If the editor route or visible publisher kind does not match, stop filling and navigate to the correct route. If it shows a login page, stop all form filling and ask the user to manually log in on that page, then reply with the exact message `已登录`. Never read, fill, or store credentials, including phone numbers, email addresses, passwords, verification codes, cookies, localStorage, sessionStorage, request headers, or browser configuration. If CAPTCHA, risk control, account verification, an ambiguous editor, or an unexpected page appears, stop for the user. Never bypass or guess through it.
4. After `已登录`, reacquire the existing tabs from `agent.browsers.get("iab")` and preferentially resume the same LOFTER tab. Continue only when that tab unambiguously shows the authenticated editor. If it still shows login, CAPTCHA, risk control, account verification, or ambiguous state, remain paused. Resume with the same run and locked `upload-manifest.json`; do not repeat the first confirmation, rebuild or change the manifest, or create a new run. Treat the tab ID only as an in-memory reference for this execution and never persist it. Distinguish the observed editor state before continuing: for an initial login resume with an empty editor, upload the locked manifest cover first and immediately observe it as the first effective content node before entering any title or body; then continue at step 6. For a recovered previously filled draft, recheck that the existing cover is the first effective content node before any further filling or final platform preview evidence. If the existing cover is not first, reposition it and re-observe; if the editor state or ordering cannot be made unambiguous, pause for the user. After a successful recheck or reposition and re-observation, never execute step 5's fresh cover upload; continue at step 6 using the recovered content.
5. Fill only from `upload-manifest.json`/the exact object returned by `build_upload_manifest`. Do not improvise content, reorder media, or upload any file absent from the manifest. In the native photo editor, upload the cover first and then every remaining image in manifest order; observe the cover as the first gallery item before entering the title, caption, or tags. In the text editor, upload the cover first and observe it as the first effective content node before entering the article body. If ordering cannot be established, pause rather than continuing.
6. For `image_post`, after all ordered images are visible in the native photo editor, enter the manifest title, use the manifest article as the short image caption, and enter the tags. For `article`, keep the text-editor flow: enter the title and full body, then upload every body image after the matching text in manifest order. Verify publisher kind, title, caption/body, tags, image count, and image order against the approved run. Capture final platform preview evidence with the submit button visible and persist `publisher_kind: photo` for `image_post` or `publisher_kind: text` for `article`; reject the preview if the kind mismatches the locked content format.
7. Stop before the final submit button. Show the final platform preview to the user and request the exact phrase `确认最终提交`. Never treat `确认发布`, `已登录`, a paraphrase, a prior message, or generic approval as the second confirmation.
8. After receiving `确认最终提交`, re-load the run state and platform preview. Run `approve_final_submit` immediately before clicking submit. If either revalidation fails or the page changed, stop without clicking.
9. Click submit exactly once. If success is clear, record the HTTPS LOFTER URL and timezone-aware publication time with `record_publication`. Preserve the final article, title, tags, manifest, source ledger, and result evidence in the run archive.
10. If the result is uncertain, record `{"result": "uncertain"}`, inspect the LOFTER profile or drafts read-only, and do not click submit again. If the exact LOFTER URL, observed title, approved manifest digest, and check time match, archive via `resolve_uncertain_publication`. Do not retry, refresh into a second submission, or infer failure from a slow response.

If upload or page structure fails before submit, use the safe pre-submit pause and report only a non-secret error. Never store passwords, cookies, session values, verification codes, CAPTCHA data, or authorization evidence in browser/publication state.
